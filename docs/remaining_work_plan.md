# Подробный план оставшихся работ

Этот документ фиксирует, что уже закрыто и что ещё осталось сделать до полноценного monocular visual SLAM pipeline поверх `yoga_cam_sub`.

## 0. Что уже закрыто

Уже есть рабочая база:

- стабильная сборка ROS 2 пакета на Windows 11 / ROS 2 Jazzy / MSVC x64;
- собственный `camera_publisher` с `Image` и `CameraInfo`;
- `image_counter` для subscriber smoke-проверок;
- `camera_slam_preflight` для проверки синхронности, `frame_id` и FPS;
- `camera_feature_monitor` для оценки visual-feature качества потока;
- запись, воспроизведение, каталогизация и JSON-отчёты по rosbag-датасетам;
- launch-файлы, smoke-тесты и полный автоматический прогон;
- импорт реальной калибровки из стандартного YAML.

То есть базовая камера-подсистема уже доведена до инженерно пригодного состояния. Дальше работа смещается с "поднять камеру" на "собрать воспроизводимый SLAM pipeline".

## 1. Ближайший обязательный этап — довести входные данные до production-like качества

### 1.1. Зафиксировать реальную калибровку камеры

Статус: частично готово, нужен реальный прогон.

Задачи:

- выполнить реальную калибровку встроенной камеры на целевом разрешении;
- сохранить итоговый `ost.yaml` или эквивалентный YAML;
- импортировать его через `scripts/import_camera_calibration.ps1`;
- прогнать `scripts/run_slam_preflight.ps1` уже с реальной калибровкой;
- записать эталонный bag после калибровки;
- зафиксировать в документации, какая именно калибровка считается эталонной.

Definition of done:

- `CameraInfo` больше не шаблонный;
- `camera_slam_preflight` не ругается на template-like calibration;
- эталонный dataset записан уже с реальной калибровкой.

### 1.2. Зафиксировать рабочие режимы камеры

Статус: частично готово.

Задачи:

- проверить несколько режимов `width/height/fps`;
- выбрать минимум два официально поддержанных профиля, например:
  - `640x360 @ 30 FPS` — базовый realtime режим;
  - `1280x720 @ 30 FPS` — режим для более богатой текстуры, если ноутбук тянет;
- для каждого профиля сохранить:
  - preflight-report;
  - feature-report;
  - короткий bag-датасет;
- зафиксировать выбранные thresholds в docs и, при необходимости, в config-шаблонах.

Definition of done:

- есть список поддержанных camera-профилей;
- для каждого профиля есть подтверждённый dataset и отчёты.

### 1.3. Зафиксировать финальный TF-контур

Статус: базовый optical TF уже есть.

Задачи:

- определить, какие frame будут использоваться в SLAM pipeline:
  - `base_link`
  - `camera_link`
  - `camera_optical_frame`
- если камера будет стоять на роботе, уточнить смещения и углы `camera_link` относительно `base_link`;
- если камера остаётся в ноутбуке, хотя бы зафиксировать текущее допущение в docs;
- добавить launch-шаблон для будущего `base_link -> camera_link`, если он понадобится.

Definition of done:

- есть согласованный минимальный TF-контур для SLAM backend.

## 2. Следующий большой этап — интеграция реального monocular SLAM backend

### 2.1. Выбрать backend

Статус: начато.

Для первого monocular-пилота выбран `ORB-SLAM3 wrapper`.
Это решение уже отражено в отдельном adapter layer и документации, но финальная runtime-валидация всё ещё зависит от внешней установки backend на целевой машине.

Нужно принять инженерное решение между вариантами:

1. `rtabmap_ros`
2. ORB-SLAM3 wrapper
3. собственный экспериментальный pipeline

Задачи:

- сравнить требования по Windows/ROS 2 совместимости;
- проверить, нужен ли stereo/depth или достаточно monocular-only;
- оценить сложность локальной сборки на Windows;
- выбрать первый backend для пилотной интеграции.

Уже сделано:

- для пилотной ветки выбран `ORB-SLAM3 wrapper`;
- добавлен документ `docs/orbslam3_backend_integration.md` с причинами выбора и ограничениями.

Definition of done:

- выбран один конкретный backend для первой интеграции;
- создан документ с причинами выбора и ограничениями.

### 2.2. Добавить адаптер запуска выбранного backend

Статус: начато.

Задачи:

- добавить launch-файл, который подключает:
  - `/camera/image_raw`
  - `/camera/camera_info`
  - `tf_static`
- вынести конфиг backend в отдельный `config/` файл;
- добавить wrapper-скрипт запуска;
- логировать входные параметры эксперимента.

Уже сделано:

- добавлен `scripts/run_orbslam3_backend.ps1`;
- добавлен `config/slam_backend.orbslam3.template.json`;
- добавлен smoke-контур `config/slam_backend.orbslam3.mock.template.json` и `scripts/orbslam3_backend_adapter_smoke_test.ps1`.

Definition of done:

- backend стартует через один reproducible launch/script.

### 2.3. Зафиксировать выходные артефакты backend

Статус: частично начато.

Задачи:

- определить, какие выходы считаются обязательными:
  - pose / trajectory;
  - map points / keyframes;
  - debug log;
  - runtime stats;
- описать, куда эти файлы/топики будут складываться;
- добавить единый каталог для результатов эксперимента.

Уже сделано:

- trajectory в формате `tum_pose_v1` теперь нормализуется в общий `trajectory_report.json`;
- runtime-log ORB-SLAM3 adapter сохраняется в experiment packet;
- путь для карты оставлен опциональным вторым шагом.

Definition of done:

- результат SLAM-прогона можно воспроизвести и сравнить между экспериментами.

## 3. Экспериментальная инфраструктура и воспроизводимость

### 3.1. Довести experiment workflow до полноценного журнала экспериментов

Статус: частично готово.

Уже сделано:

- есть reproducible experiment packet по bag;
- есть общий каталог experiment packet;
- есть offline-сравнение baseline/candidate по входным SLAM-метрикам;
- есть trajectory-report по backend output и offline-сравнение длины/скорости trajectory между экспериментами;
- есть шаблонные поля для ручной оценки backend (`tracking_lost`, `map_quality`, заметки).
- есть backend-agnostic runner для внешнего SLAM backend и mock smoke-проверка этого слоя;
- есть Markdown/CSV-сводка по каталогу экспериментов.

Осталось сделать:

- добавить шаблон регрессии "baseline vs candidate" для одного и того же эталонного bag.

Definition of done:

- можно сравнивать несколько прогонов на одном bag не только по входным отчётам, но и по выходным SLAM-результатам.

### 3.2. Создать набор эталонных датасетов

## 5. Технический долг и улучшения архитектуры

### 5.1. Разделить reusable telemetry в отдельный слой

Сейчас часть логики размазана по runtime-нодам. Позже полезно выделить:

- общий summary formatter;
- общую модель experiment report;
- helper для безопасного запуска подчинённых ROS-процессов в PowerShell.

### 5.2. Подумать о message_filters / sync policy

Сейчас `CameraInfo` публикуется синхронно с кадром и этого достаточно. Но при подключении внешних источников или backend может понадобиться:

- explicit sync policy;
- проверка timestamp drift;
- отдельный sync-monitor.

### 5.3. Подумать о transport-режимах

Пока используется raw image topic. Если позже появятся ограничения по пропускной способности, нужно будет оценить:

- `image_transport`;
- compressed transport;
- влияние на SLAM feature quality.

## 6. Что можно считать следующей вехой проекта

Следующая большая веха: **"Monocular SLAM backend запускается на эталонном bag и выдаёт воспроизводимый результат"**.

Для достижения этой вехи минимально нужно:

1. реальная калибровка;
2. согласованный TF;
3. выбранный SLAM backend;
4. launch-адаптер для backend;
5. хотя бы один эталонный dataset;
6. experiment manifest + сохранение результата backend.

## 7. Рекомендуемый порядок дальнейшей работы

1. Реальная калибровка
2. Эталонный dataset после калибровки
3. Выбор SLAM backend

### Порядок B — если хотим ещё укрепить инфраструктуру до backend

## 8. Мой рекомендуемый следующий шаг прямо сейчас

Самый логичный следующий инженерный шаг: **довести пилотную ORB-SLAM3 интеграцию до первого реального запуска на эталонном bag**.

Если идти без лишних скачков, то порядок такой:

1. поставить или собрать внешний ORB-SLAM3 backend / bridge на целевой машине;
2. заполнить реальные пути в `config/slam_backend.orbslam3.template.json`;
3. запустить backend на эталонном experiment packet и зафиксировать первый реальный trajectory-report.
